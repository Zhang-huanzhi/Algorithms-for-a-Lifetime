这是一个非常经典的 **“Python 大整数陷阱”**！

你直觉上觉得复杂度是 $O(N)$（循环 $10^5$ 次），按理说 Python 跑 $10^5$ 次循环只需要 0.05 秒左右，绝对不会超时。

但问题在于：**你以为的常数级运算 $O(1)$，实际上变成了超级耗时的运算！**

让我们看看你当时写的代码核心部分：

```python
for _ in range(n):
    # ...
    elif t == "*":
        ans *= a  # <--- 罪魁祸首在这里！

    outs.append(ans % 10000)  # <--- 这里也被连累了！
```

### 为什么会 TLE？

在 Python 里，整数的大小是没有上限的（高精度整数/大数机制）。但这并不代表大数运算是“免费”的。

假设测试数据恶意卡你：
- 操作包含 $10000$ 次 `* 100`。
- 最终的 `ans` 会达到多大？大约是 $100^{10000} = 10^{20000}$。
- 这意味着 `ans` 是一个**拥有两万多位数字（甚至几十万位数字）的超级庞然大物**！

一旦数值变得如此巨大：
1. **乘法 `ans *= a` 不再是 $O(1)$**：
   计算机底层的 CPU 只能瞬间算 64 位以内的乘法（大约 18 位数以内）。当数字达到几万位、几十万位时，Python 必须在内存中开辟巨大的数组，用高精度乘法算法模拟竖式计算。每次乘法都需要花费极多的时间。
2. **取模 `ans % 10000` 变成灾难**：
   大整数除以一个数求余数，本质上是对几十万位数字做长除法。循环 $10^5$ 次，每次都对一个几万到几十万位的巨型数字做一次大整数除法求模，**单次运算耗时就会从纳秒级别飙升到毫秒甚至秒级别**！

所以，虽然你的循环只走了 $N = 10^5$ 次，但因为 `ans` 像滚雪球一样越来越巨大，**总耗时实际上是 $O(N \times \text{大整数位数})$**，甚至可能达到几十秒，因此必然超时（TLE）。

---

### 对比：为什么每一步取模就飞快？

```python
if t == "*":
    ans = (ans * a) % 10000
```
如果你**每一步都取模**：
- `ans` 永远卡在 $0 \le ans < 10000$ 之间（最多也就是个 4 位数）。
- 每次乘法只是简单的 `4位数 * 2位数`。
- 这是最纯正的 **CPU 硬件级 64 位整数运算**，耗时只需 **1 纳秒**。
- $10^5$ 次硬件运算加起来，连 0.05 秒都用不到，直接 AC。

这也是为什么在算法竞赛中，只要题目要求求模，**所有中间变量必须步步取模**，决不能让它在内存里无休止地膨胀。
