在算法竞赛和刷题中，**没有绝对的好与坏，但有极其明确的“行业共识”和“场景偏好”**。

一句话先给结论：
> **做“树/图论/前缀和/线段树/数位DP”等偏数学和结构的算法题，强烈推荐 1-based；**
> **做“字符串/矩阵/LeetCode风格的常规模拟题”，推荐 0-based。**

---

### 为什么顶级选手在很多算法题中偏爱 1-based？

#### 优势 1：处理“前缀和”极其自然，消灭边界特判
这是 1-based 最具威力的地方。
* **0-based 前缀和**：
  求区间 $[L, R]$ 的和是 `pre[R] - pre[L-1]`。
  当 $L = 0$ 时，$L - 1 = -1$，在 Python 会读到末尾元素（产生致命逻辑 Bug），在 C++/Java 会直接越界崩溃。你不得不写：
  `cost = pre[R] - (pre[L - 1] if L > 0 else 0)`（极其繁琐）
* **1-based 前缀和**：
  定义 `pre[0] = 0`。
  求区间 $[L, R]$ 的和**永远是 `pre[R] - pre[L-1]`**。
  当 $L = 1$ 时，算的是 `pre[R] - pre[0] = pre[R] - 0`，**完全不需要特判！**

#### 优势 2：天然契合“空状态 / 哨兵”
在图论、树、链表中，`0` 可以作为一个天然的**空节点（Null / None）**。
* 比如树的子节点：`left_child[u] = 0` 就代表没有左儿子，不需要额外用 `-1` 或 `None` 来表示。
* 在线段树/二叉堆中，节点 $k$ 的左儿子是 $2k$，右儿子是 $2k+1$（如果是 0-based，公式是 $2k+1$ 和 $2k+2$，写起来容易看花眼）。

#### 优势 3：与大多数题目描述“无缝对齐”
像 Codeforces、AtCoder、各大高校校赛，**95% 以上的题面都是从 1 到 N 编号**的。
如果用 1-based，读入的数据可以直接用，不需要在脑子里做一层 `s -= 1`、`u -= 1` 的转换，能少死很多脑细胞。

---

### 什么时候必须/推荐用 0-based？

1. **LeetCode 刷题**：
   * LeetCode 的入参全是 Python 原生 `List`，默认就是 0-based。强行改 1-based 往往需要 `[0] + nums`，显得多余。
2. **字符串相关（KMP、AC自动机、字符串哈希除外）**：
   * 字符串默认下标是 0，取 `s[0]` 最自然。
3. **位运算与状态压缩 DP**：
   * 计算机的二进制位第 0 位、第 1 位……状态压缩天然绑定 0-based。
4. **环形数组 / 模运算**：
   * 比如循环移位：`(i + 1) % n` 很优雅。如果是 1-based，写模运算就得变成 `(i - 1 + 1) % n + 1`，非常别扭。

### 💡 终极实战建议

| 题目类型 | 推荐体系 | 核心原因 |
| :--- | :--- | :--- |
| **前缀和 / 差分** | **1-based** | 避免 `L=0` 时的越界特判 |
| **树 / 图论算法** | **1-based** | `0` 可以当做不存在的空节点 |
| **线段树 / 树状数组 (BIT)** | **1-based** | 树状数组的 `lowbit` 运算**必须**从 1 开始 |
| **状态压缩 / 位运算** | **0-based** | 对应二进制的第 0 位到第 $n-1$ 位 |
| **LeetCode 简单模拟/数组题**| **0-based** | 契合原题传入的参数结构 |

**给你的记忆口诀**：
> **遇到“求和算区间”、“建树跑图论”，数组多开 1 格，直接 1-based 起手；**  
> **遇到“字符串”、“位运算”、“LeetCode 原生题”，老老实实 0-based。**
