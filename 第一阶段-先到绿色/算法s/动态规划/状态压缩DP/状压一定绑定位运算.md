---

在算法竞赛和刷题中，**“状压 DP”和“位运算”确实是 100% 锁死绑定的。**

这两者之所以形影不离，本质原因可以用一句话概括：
**“状态压缩”的本质就是把一个复杂的集合或数组压缩成一个“整数”；而“位运算”是计算机底层处理这个“整数”时最自然、最快、唯一的工具。**

我们可以从以下四个方面把这个逻辑彻底理清：

### 1. 完美的“概念映射”（把现实事物变成二进制）
在很多 DP 问题中，我们需要记录多个事物的状态。例如：
*   8 个城市，每个城市“去过”或“没去过”。
*   7 个格子，每个格子是“黑”还是“白”。
*   5 个物品，每个物品“选了”还是“没选”。

这本质上都是一个**布尔数组 (Boolean Array)**。比如 `[True, False, True]`。
而在计算机世界里，只有 0 和 1。我们非常自然地可以把 `True` 当作 `1`，`False` 当作 `0`。
那么 `[True, False, True]` 就变成了二进制的 `101`。
二进制的 `101` 在计算机里就是十进制的数字 `5`！

**这就叫“状态压缩”**：把一个需要用数组来存的复杂状态，**压缩**成了一个普普通通的整数（比如 5）。

### 2. 只有“位运算”能拆解这个被压缩的整数
既然你把一个数组压缩成了一个数字 `5`，在写 DP 转移方程时，你肯定要问：
*   *“第 0 个格子是黑的还是白的？”*
*   *“我要把第 1 个格子涂黑，状态会变成什么？”*

面对数字 `5`（二进制 `101`），普通的加减乘除是很难回答这些问题的（你用加减乘除算 `101` 的第二位是几，非常麻烦）。
**但位运算天生就是干这个的！**
*   **查询第 `i` 位是 0 还是 1**：`(5 >> i) & 1`
*   **把第 `i` 位变成 1**：`5 | (1 << i)`
*   **把第 `i` 位变成 0**：`5 & ~(1 << i)`
*   **把第 `i` 位翻转**：`5 ^ (1 << i)`

你看，位运算就是我们解开“压缩包”的唯一且最完美的钥匙。

### 3. 极速的集合运算（数学上的绝妙配合）
在状态压缩 DP 中，状态通常代表一个**集合**。状态之间的转移，本质上是集合的交、并、补运算。
如果你用 Python 的 `set()` 或者 `list`：
*   求两个集合的交集：可能需要循环遍历，时间复杂度 $O(N)$。

但如果用整数和位运算：
*   **求交集 (两个状态的公共部分)**：`A & B`
*   **求并集 (合并两个状态)**：`A | B`
*   **判断 A 是否是 B 的子集**：`(A & B) == A`
*   **判断两个状态有没有冲突（没有交集）**：`(A & B) == 0`

**上面所有的位运算，在 CPU 中只需要 1 个时钟周期就能完成！** 是真正的 $O(1)$。
就像这道题里，我们要判断上下两行有没有重叠的黑块，直接 `overlap = prev & curr`，瞬间完成对比，这是任何其他数据结构都做不到的极速。

### 4. 动态规划的刚需：数组索引（Index）
动态规划 (DP) 的核心思想是**查表（记忆化）**。我们需要一个数组来存之前算过的结果，也就是 `dp[状态] = 最小花费`。

*   如果你用数组表示状态：`dp[[True, False, True]]` —— **报错！** 数组和列表不能作为数组的下标（索引）。
*   即便用 Hash 表（字典）：`dp[(True, False, True)]` —— 虽然可以存，但 Hash 表的查找速度远慢于数组。
*   但如果你用整数：`dp[5]` —— **完美！** 直接定位内存地址，速度拉满。

### 总结
之所以“状压一定绑定位运算”，是因为：
状压 DP 为了满足 DP 对**“极速查表”**的需求，被迫把**“状态（数组/集合）”**变成**“整数”**；
而一旦变成了整数，我们就必须使用**“位运算”**来完成对这个整数内部细节的**“增删改查”**。

这就是它们锁死绑定的根本原因。只要你看到数据范围 $N \le 20$，立刻在脑子里把事物联想成 `01010` 这样的二进制串，然后顺理成章地掏出位运算，这就是一套标准的思维定式。
