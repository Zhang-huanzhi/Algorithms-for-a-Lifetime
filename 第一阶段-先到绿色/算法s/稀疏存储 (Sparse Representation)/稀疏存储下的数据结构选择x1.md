### 一、 算法上（刷题、竞赛、面试）

在算法题中，处理稀疏数据或矩阵，基本被以下三种结构垄断：

#### 1. 邻接表 (Adjacency List)
* **结构**：`list` of `list`。
* **核心作用**：保存**“拓扑/连接关系”**。
* **典型场景**：图的遍历（DFS/BFS）、树的表示、本题中的“食材到菜品的反向关联”。
* **特点**：最适合需要“顺着一个节点找出所有相关联节点”的场景。

#### 2. 查找表 (Hash Set / Map)
* **结构**：`set` 或 `dict` (C++ 中为 `unordered_set/map` 等)。
* **核心作用**：**$O(1)$ 的存在性判定、去重、或离散映射**。
* **典型场景**：记录已访问的节点（`visited` 集合）、本题中记录“食材在哪天被克服”（`brr_rule` 字典）。
* **特点**：不需要遍历关联关系，只想快速知道“某个元素在不在”或“它的属性是什么”。

#### 3. 三元组 (Coordinate List / COO)
* **结构**：元素为 `(row, col, value)` 的一维列表。
* **核心作用**：**低成本记录“带权重的稀疏边/点”，配合排序算法使用**。
* **典型场景**：
  * **最小生成树算法（Kruskal）**：把所有边存为三元组 `(u, v, weight)`，然后按权重排序。
  * **稀疏矩阵的坐标表示**：直接存非零元，后续通过自定义双指针或排序来处理。
* **特点**：本身不具备快速查询能力，但数据结构极其简单，**非常便于进行全局排序或格式转换**。

### 二、 工程上（工业级开发、库函数、科学计算）

在实际工程项目中（如机器学习、图像处理、3D 物理引擎），面对数亿级别的稀疏数据，开发者**几乎从不手写**上述底层结构，而是直接调用成熟的数学库（如 Python 的 `SciPy`、C++ 的 `Eigen` 等），其核心结构如下：

#### 1. CSR / CSC (行/列压缩存储)
* **特点**：工程上的**绝对霸主**。将稀疏矩阵压缩为三个紧凑的一维数组。
* **优势**：内存占用达到物理极限的极小，且对现代 CPU 缓存极其友好，做矩阵乘法（如神经网络、图形渲染）时速度极快。

#### 2. 各种工程变体（如 Block CSR, Dia 等）
* **特点**：针对特定物理规律（如对角线矩阵、分块矩阵）设计的特殊压缩结构。

#### 3. 库的使用逻辑
在工程中，标准的开发流水线通常是：
1. 用 **三元组（COO）** 或 **LIL（邻接表）** 在业务层动态收集、组装数据。
2. 构建完成后，调用库函数一键转换为 **CSR/CSC** 格式，送入底层进行高性能的并行计算（GPU/多线程）。
