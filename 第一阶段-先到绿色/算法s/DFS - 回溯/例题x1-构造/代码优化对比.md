# 未优化 TLE
``` python
import sys
from collections import deque, defaultdict, Counter


def main():

    n, k = map(int, sys.stdin.readline().strip().split())

    outs = []

    # 这很明显，暴力？这还得自己构造
    # N比较小，还是暴力吧DFS
    arr = []
    arr.append((1, 0, []))

    while arr:
        pos, curr, path = arr.pop()

        if pos == n + 1:
            if curr == k:
                outs.append(' '.join(map(str, path)))
            continue

        rem = k - curr

        for x in range(rem // pos, -1, -1):
            arr.append((pos + 1, curr + pos * x, path + [x]))

    print('\n'.join(map(str, outs)))

if __name__ == "__main__":
    main()
```

# 优化 AC
``` python
import sys
from collections import deque, defaultdict, Counter


def main():

    n, k = map(int, sys.stdin.readline().strip().split())

    outs = []

    # 这很明显，暴力？这还得自己构造
    # N比较小，还是暴力吧DFS
    arr = []
    arr.append((1, 0, []))

    while arr:
        pos, curr, path = arr.pop()

        if curr == k:
            outs.append(" ".join(map(str, path + [0] * (n - pos + 1))))
            continue

        if pos == n:
            rem = k - curr

            if rem % n == 0:
                outs.append(" ".join(map(str, path + [rem // n])))

            continue

        rem = k - curr

        for x in range(rem // pos, -1, -1):
            arr.append((pos + 1, curr + pos * x, path + [x]))

    sys.stdout.write("\n".join(outs))


if __name__ == "__main__":
    main()
```


这两份代码结构高度一致，但**正是那关键的几行剪枝与数学计算，让代码的运行状态数产生了 $10^4$ 倍（上万倍）的断崖式差距**，从而从 TLE 变为 AC。

以下是两份代码的**逐项深度对比**：

---

### 对比总览表

| 对比维度 | 未优化版本 (TLE) | 优化版本 (AC) | 差异带来的影响 |
| :--- | :--- | :--- | :--- |
| **搜索深度** | 搜满全部 $N$ 层（`pos == n + 1` 结束） | 搜到第 $N-1$ 层（`pos == n` 结束） | **核心瓶颈**：搜索树规模从 $10^{10}$ 骤降到 $10^6$ 级 |
| **第 $N$ 项确定方式** | 循环暴力枚举 $A_N$ 的所有可能值 | **$O(1)$ 数学计算**：`rem // n` | 彻底消除了最后一层的庞大分支 |
| **中间提前结算** | 无（即使 `curr == k` 仍会逐层入栈 0） | **有**（`curr == k` 时直接补 0 输出并跳过） | 减少了无意义的入栈/出栈开销 |
| **输出效率** | `print('\n'.join(map(str, outs)))` | `sys.stdout.write('\n'.join(outs))` | 略微减少 I/O 耗时和多余的 `map(str, ...)` 转换 |
| **运行结果** | **TLE（超时）** | **AC（通过，耗时约 0.2~0.4s）** | **质的飞跃** |

---

### 关键差异深度解析

#### 1. 核心差异：第 $N$ 项的枚举 vs 数学计算（决定生死的一步）

* **未优化版 (TLE)**：
  ```python
  if pos == n + 1:
      if curr == k:
          outs.append(' '.join(map(str, path)))
      continue
  ```
  * **逻辑**：DFS 一直跑到第 $n$ 层时，仍然执行下面的 `for x in range(rem // pos, -1, -1)`，把 $A_N$ 从 $0$ 到 $rem/N$ 的所有值**一个个压入栈中**，直到 `pos == n + 1` 才去检查 `curr == k`。
  * **代价**：它遍历了所有满足 $\sum_{i=1}^N i \cdot A_i \le K$ 的状态。
    * 当 $N=2, K=2 \times 10^5$ 时，状态数约为 $\frac{K^2}{4} \approx \mathbf{10^{10}}$ 次循环，**必然严重超时**。

* **优化版 (AC)**：
  ```python
  if pos == n:
      rem = k - curr
      if rem % n == 0:
          outs.append(" ".join(map(str, path + [rem // n])))
      continue
  ```
  * **逻辑**：DFS 到达第 $n$ 项时**立刻打住**，不再进循环。直接利用等式约束计算 $A_N = rem / n$，只在能够整除时记录答案。
  * **效果**：最后一层枚举的开销直接降为 $O(1)$，总状态数被严格限制在 $O(N \times \text{解的数量}) \approx \mathbf{3 \times 10^6}$ 次以内，**提速达数千倍**。

---

#### 2. 次要优化：`curr == k` 时的提前结算

* **未优化版 (TLE)**：
  * 如果在第 $2$ 项时总和就已经恰好达到了 $K$，它仍会把后面的项逐个赋值为 $0$ 入栈、出栈，一直走到第 $N+1$ 项。
* **优化版 (AC)**：
  ```python
  if curr == k:
      outs.append(" ".join(map(str, path + [0] * (n - pos + 1))))
      continue
  ```
  * **效果**：一旦和已经凑齐，后续所有元素必定只能是 $0$。直接通过 `[0] * (n - pos + 1)` **瞬间补齐并剪枝返回**，跳过了后续若干层的进出栈操作。

---

#### 3. I/O 性能与冗余操作清理

* **未优化版 (TLE)**：
  ```python
  print('\n'.join(map(str, outs)))
  ```
  * 这里的 `outs` 内部元素本来就已经是构建好的字符串了（`" ".join(...)`），外层的 `map(str, outs)` 属于多余的二次遍历转换。
* **优化版 (AC)**：
  ```python
  sys.stdout.write("\n".join(outs))
  ```
  * 去掉了无意义的 `map(str, ...)`，直接通过底层 I/O 流输出，在 $3 \times 10^5$ 行大规模输出时更加平稳。

---

### 总结
未优化版本属于**“盲目遍历所有可能前缀”**；而优化版本通过**“方程降维直接求最后一项”**，将原本指数级/多项式级膨胀的搜索树，压缩成了只贴着“有效解”生长的极简搜索树。这就是从 TLE 到 AC 的根本原因。
