并不是 $O(N^2 \log N)$。实际的整体时间复杂度非常低，只有：

$$\sum O(N \log N + 80N)$$

其中 $\sum N \le 10^5$。对于全套测试用例，总计算量在 **$10^7$ 次运算**左右，在 Python 中运行仅需 **0.2 ~ 0.3 秒**。

我们可以把代码拆开，一步步计算它的真实复杂度：

---

### 1. 拆解单次测试用例的复杂度

#### 第一步：数组排序
```python
arr.sort()
```
* **复杂度**：$O(N \log N)$。

---

#### 第二步：实数二分查找
```python
for _ in range(80):
    mid = (low + high) / 2
    if count_ge(mid) >= x:
        ...
```
* **复杂度**：这里循环固定执行 **$80$ 次**（因为是浮点数二分，我们用固定的次数来保证精度）。
* 这是一个**常数** $O(80)$，它**不随 $N$ 的增大而增大**，所以不能看作 $O(N)$。

---

#### 第三步：分析 `count_ge(mid)` 函数内部的复杂度
每一次二分循环中，我们都会调用一次 `count_ge` 函数：

1. **二分边界定位**：
   ```python
   idx_2W = bisect_left(arr, 2 * W)
   idx_W = bisect_left(arr, W)
   ```
   由于 `arr` 已经排好序，这两次二分查找的复杂度是 **$O(\log N)$**。

2. **单层循环计算 `req`**：
   ```python
   for i in range(idx_2W, n):
       ...
   ```
   * 这个循环从 `idx_2W` 遍历到 `n`。
   * **最坏情况**下（当 $W$ 很小时），需要遍历整条数组，循环执行 $N$ 次。
   * 循环内部只有简单的数学运算（`log2`、位移等），每一次运算都是 $O(1)$ 的。
   * 因此，这个循环的复杂度在最坏情况下是 **$O(N)$**。

---

### 2. 组合单次测试用例的复杂度

我们将上面几步组合起来：

* **排序**：$O(N \log N)$
* **二分查找整体**：
  $$\text{循环次数} \times \text{单次 Check 复杂度} = 80 \times (O(\log N) + O(N)) \approx O(80N)$$

因此，单个测试用例的总时间复杂度为：
$$O(N \log N) + O(80N) = O(N \log N + 80N)$$

---

### 3. 为什么你直觉上觉得是 $O(N^2 \log N)$？

你可能把以下两点混淆了：
1. **二分搜索的性质**：我们二分的是**实数答案 $W$**（它的范围是 $[0, 10^9]$），而不是在 $N$ 个元素的数组里二分。
   * 如果是对 $N$ 个元素进行二分，循环次数是 $\log N$ 次。
   * 我们这里是实数二分，循环次数是固定的常数 $80$ 次。
2. **嵌套关系**：
   * 二分查找循环了 $80$ 次。
   * 每次循环内部有一个 $O(N)$ 的遍历。
   * 它们是**乘法**关系：$80 \times O(N) = O(80N)$，绝对不会产生 $N^2$。

### 总结
因为题目限制了所有测试用例的 $N$ 之和 $\sum N \le 10^5$，所以即使把所有测试用例累加起来，总运行时间也只是：
$$O(\sum N \log N) + 80 \times O(\sum N)$$
这对于现代计算机来说，只是眨一下眼就能算完的超低复杂度。
