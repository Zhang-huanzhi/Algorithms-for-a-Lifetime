这道题中的 `history` 优化，是一个非常经典且高级的**算法工程优化技巧（常数优化）**。

在很多语言（尤其是 Python）的算法竞赛中，即使你的算法时间复杂度是正确的（比如这道题的 $O(H^2 W)$），但如果忽视了**内存分配和垃圾回收**的开销，依然会卡在 TLE（运行超时）上。

`history` 优化的本质，就是**用“状态回滚（Rollback）”代替“销毁重建”，将空间重置的复杂度从 $O(H \times W)$ 暴降到 $O(W)$。**

---

### 一、 致命的瓶颈：全量重置

在我们的算法中，外层循环要跑 $125,000$ 次（因为有 $\frac{H(H+1)}{2}$ 对左右/上下边界）。

在每一轮中，我们都需要一个频数表 `freq`。因为最大可能的前缀和是 $H \times W = 250,000$，所以这个 `freq` 数组的长度必须是 $250,001$。

为了保证下一轮循环的数据不被污染，我们在进入下一轮前，必须把 `freq` 恢复成全 0。

#### 做法 A（直观但致命的写法）：
```python
# 每次循环开始时，重新开辟一个全 0 数组
freq = [0] * 250001
```
* **代价分析**：
  在 Python 中，创建一个大小为 $25万$ 的列表，操作系统需要申请内存、清零、创建 Python 对象。
  这个操作要重复执行 $125,000$ 次。
  $$\text{总操作数} = 125,000 \times 250,001 \approx \mathbf{3.1 \times 10^{10}} \text{（310 亿次）}$$
  这直接导致程序卡死，耗时可能长达数分钟，理论上正确的 $O(H^2 W)$ 算法彻底作废。

---

### 二、 核心发现：极度稀疏的修改

我们静下心来观察每一次内层循环：
虽然 `freq` 数组的容量高达 $250,001$，但在单次内层循环中，列数 $W$ 只有 $500$。
也就是说，**我们最多只会往 `freq` 数组里填入 $500$ 个数。**

这意味着：
* 每次循环结束时，`freq` 数组中 **99.8% 的位置（约 249,500 个位置）本来就已经是 0 了**。
* 我们根本不需要去重置那些已经是 0 的位置！我们只需要把那 **0.2% 被我们加过 1 的位置改回 0** 即可。

---

### 三、 妙手：`history` 局部回滚

为了实现“精准重置”，我们引入了 `history` 列表：

1. **记录修改**：
   在内层循环中，每当我们修改了 `freq` 的某个位置：
   ```python
   freq[curr_sum] += 1
   history.append(curr_sum)  # 像“日志”一样记下我们修改了哪个位置
   ```
2. **精准回滚**：
   当这一轮循环结束，需要清空 `freq` 时，我们不重建数组，而是跟着“日志”去撤销修改：
   ```python
   for val in history:
       freq[val] = 0  # 哪里脏了洗哪里
   ```

#### 优化后的代价分析：
由于 `history` 的长度最多只有 $W + 1 = 501$，所以重置操作的计算量变成了：
$$\text{总重置操作数} = 125,000 \times 500 = \mathbf{62,500,000} \text{（6250 万次）}$$

从 **310 亿次** 骤降到 **6250 万次**，整整提升了 **500 倍** 的运行速度！

---

### 四、 对比：销毁重建 vs 局部回滚

| 特性 | 销毁重建 (`freq = [0] * 250000`) | 局部回滚 (`history` 撤销) |
| :--- | :--- | :--- |
| **重置时间复杂度** | $O(H \times W)$ （每次都要处理整个数组空间） | **$O(W)$** （只处理发生改变的局部空间） |
| **内存申请** | 极度频繁，产生海量内存碎片，触发 GC（垃圾回收） | **只在程序开头申请一次**，之后全程复用同一块内存 |
| **Python 底层开销** | 极高（涉及 C 语言级别的 `malloc`） | 极低（纯粹的数组索引赋值 `0`） |
| **运行效果** | **TLE（超时）** | **AC（通过）** |

### 总结

`history` 优化体现了算法工程中非常重要的一个哲学：**“不要试图毁灭世界再重建它，你只需要悄悄抹去你留下的痕迹。”** 

在撤销操作成本极低（只需赋值 0）而空间极大的场景下，这种“状态回滚”的设计模式是写出高性能代码的必备大杀器。
