# 正文
假设出题人给的数据是这样的顺序：  
union(1, 2) -> union(2, 3) -> union(3, 4) ... 一直循环到 union(99999, 100000)。

我们来模拟一下你的代码是怎么运行的：

1. union(1, 2)：find(1) 是 1，find(2) 是 2，执行 parent[1] = 2。树变成了 1 -> 2。
    
2. union(2, 3)：find(2) 是 2，find(3) 是 3，执行 parent[2] = 3。树变成了 1 -> 2 -> 3。
    
3. union(3, 4)：find(3) 是 3，find(4) 是 4，执行 parent[3] = 4。树变成了 1 -> 2 -> 3 -> 4。
    

出题人在偷偷建好这条长达 10 万的链条后，图穷匕见，发出了最后一条指令：  
**请告诉我，1 和 100000 连通吗？（也就是调用 find(1)）**

这时候，你的 find(1) 终于开始工作了，它准备进行伟大的“路径压缩”：

``` python
def find(self, x):
    if self.parent[x] != x:
        self.parent[x] = self.find(self.parent[x]) # 开始递归！
    return self.parent[x]
```

为了找到 1 的根，它会调用 find(2)，find(2) 调用 find(3)，find(3) 调用 find(4)......

 1. 为什么会 RE（Runtime Error）？

在 Python 中，函数自己调用自己（递归）是需要消耗系统栈空间的。为了防止死循环把内存撑爆，Python 默认的**最大递归深度只有 1000 层**。  
而你这棵树有 10 万层深！当你的代码递归到 find(1001) 的时候，Python 解释器直接崩溃，抛出 RecursionError。  
**这就是你在 AtCoder 拿到 RE 的直接原因。**

 2. 为什么会 TLE（Time Limit Exceeded）？

假设你用 sys.setrecursionlimit(200000) 强行解除了 Python 的递归限制，不报 RE 了，会怎样？  
由于这棵树有 10 万层深，调用一次 find(1) 就需要执行 10 万次函数调用。在 Python 中，函数调用的开销（Overhead）是非常巨大的。  
虽然你的“路径压缩”在这 10 万次调用结束后，终于把树压扁了，**但是这“第一次”的代价太惨重了**。如果出题人多搞几次这种局部极深的链，你的程序就会因为函数调用次数过多而严重超时（TLE）。
