# 前言

理解了你是怎么死的，你就明白为什么一定要优化了：**你必须防止树变成单链。**

你原来的模板：**只有路径压缩（事后补救），没有按秩合并（事前预防） + 致命的递归写法**。  
在随机数据下，它跑得飞快；但在 AtCoder 的恶意构造数据下，它会被直接拉成一条直线，然后被 Python 的 1000 层递归限制一波带走。这就是为什么你要去优化它的根本原因。

# 按秩合并（预防为主）

为什么要在模板里加上 size 数组？

``` python
# 小树挂大树
if self.size[root_x] > self.size[root_y]:
    self.parent[root_y] = root_x
```

因为如果加上这行代码，面对 union(1, 2), union(2, 3), union(3, 4) 这种恶意数据：

- 合并 1 和 2，变成一棵大小为 2 的树（根是 1）。
    
- 合并 2 和 3 时，3 是一棵大小为 1 的树，1（2的根）是大小为 2 的树，代码会**强制把 3 挂在 1 的下面**，而不是把 1 挂在 3 的下面！  
    结果树变成了：
    

```
   1
   / \
  2   3
```

无论出题人怎么按顺序给数据，**只要有“按秩合并”，这棵树的深度永远不会超过** log⁡2(N)。10万个节点，深度最多只有 17 层！17 层的递归，瞬间就跑完了，绝对不会 RE，也绝对不会 TLE。
